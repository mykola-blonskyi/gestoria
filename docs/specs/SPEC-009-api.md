# SPEC-009 — REST API (`GestorIA.Api`)

**Status:** Draft · **Phase:** 3 · **ADRs:** 0005, 0006, 0007

## 1. Principles
Versioned (`/api/v1`), JSON, OpenAPI 3.1 generated from code, problem+json errors (RFC 9457). Money as strings with 2 decimals in DTOs (`"1234.56"`), dates ISO-8601.

> **v1.0 trim (2026-09-18).** Idempotency keys and cursor pagination wait for a second user and a large collection. One user with four filings a year has neither problem. The versioned path, OpenAPI generation and problem+json stay, because they cost nothing now and are expensive to retrofit.

## 1.1 Built so far (#66, #68, #69, #70, #71, #72, #73, #74, #75, #88, #94)

Neither needs the key. OCR reachability joins readiness when the OCR service does (§2).
- `GET /api/v1/config/tax-years` and `GET /api/v1/config/tax-years/{year}`: each year's `configHash`, usable regions and declared gaps (SPEC-007 §3), read through `TaxYearConfigLoader` from the files copied next to the binary (`TaxYears:Directory` overrides). An unknown year is a 404.
- `POST /api/v1/set-aside/estimate?taxYear=YYYY`: the body is the console's input file byte for byte (`src/GestorIA.Cli/README.md`), parsed by the console's own parser, so both refuse the same inputs. The answer is `SetAsideResult` with money as two-decimal strings, the hold-back share as its exact decimal fraction, the trace in the engine's order and the notices. `NextPayment` carries a `filing` (`ingreso`, `aDeducir` or `negativa`), AEAT instrucciones del modelo 130 casilla 19: `ingreso` for a positive result, `aDeducir` for a negative one before Q4 (carried to a later quarter), `negativa` for a zero result or a negative one in Q4 (nothing left to carry). The engine derives it, not the web layer. The estimate also carries `annualTrueUpDueFrom`/`annualTrueUpDueBy`, the same window the annual true-up endpoint's own `dueFrom`/`dueBy` compute.
- The taxpayer profile (#69, `src/GestorIA.Api/Profiles/`), stored in PostgreSQL (ADR-0006) through EF Core, migrated as the API starts:
  - `GET /api/v1/profiles` lists the stored profiles; `POST /api/v1/profiles` stores one (201 with `Location`); `GET` and `PUT /api/v1/profiles/{id}` read and replace it; an unknown id is a 404 `profile-not-found`. Local mode keeps one profile per installation, held by the database (a unique index on an always-true `Singleton` column), so concurrent creates store exactly one: a second `POST` is a 409 `profile-exists` naming the first. The tax year is a field of the profile, so changing year is a `PUT`.
  - The body is `ProfileInputDocument`: `taxYear`, `region`, `employment { ingresos, seguridadSocial }`, `activity { alta, previousYear, newActivity }` and `projection { ingresos, gastos, baseCotizacion }`, the console input file's profile and projection. The two either-or facts are objects tagged by `kind`: `previousYear` is `{ "kind": "noActivity" }` or `{ "kind": "rendimientoNeto", "rendimientoNeto": "-1234.56" }`, `newActivity` is `{ "kind": "established" }` or `{ "kind": "started", "period": "first" | "following", "ingresosFromFormerEmployer": "0.00" }`. Amounts are strings in euros with at most two decimals and twelve digits, so the `numeric(18,6)` columns hold them exactly. A body of the wrong shape is refused at its first wrong field; a body of the right shape has every value checked and every refused one named at once in `errors`: the year must have a configuration, the region must be in it, the alta must fall in the year or before, the base de cotización must be a base of the year's tables (LGSS art. 308.1.a 3.ª).
  - `GET /api/v1/profiles/{id}/set-aside/estimate?asOf=Qn` runs the set-aside estimator on the stored profile and answers `SetAsideEstimate`. The actuals come from the profile's classified movements (#73, below). With no movement imported, the projection covers every month of alta, and for a golden with no actuals (G12, G16, G22) the answer equals the input file's, step by step. Only `ledger` differs: the input file's answer has `null` there. A year whose configuration lacks what the estimate needs is a 422 `config-gap`: every 2026 estimate today, since `2026.json` declares its renta window and Q4 Modelo 130 deadline unpublished.
  - `GET /api/v1/profiles/{id}/export` answers everything stored for the profile in one versioned document (§2.1), with `Cache-Control: no-store` and `Content-Disposition: attachment; filename="gestoria-export-YYYY-MM-DD.json"`, the day of the export in Madrid and nothing about whose it is (#74). `DELETE /api/v1/profiles/{id}` deletes the profile and every row that belongs to it and answers 204; the rows go with it through their foreign keys' `ON DELETE CASCADE`, in one statement. Nothing is kept. Both answer an unknown id with 404 `profile-not-found`. `tests/GestorIA.Api.Tests/ProfileDeletion.cs` is the documented deletion test (SPEC-013 §4): it reads every table from the EF Core model, requires each to hold a row before the delete and none after, so a table added later is covered without editing it.
  - `POST /api/v1/profiles/restore` stores an export back into an empty installation (§2.2, #75).
  - Nothing about the profile is logged (SPEC-013 §2): `ProfileNotLogged` captures every log category at Trace, EF Core's SQL included, while a profile is created, refused, replaced, read, estimated, exported, deleted and restored, and finds none of its amounts and nothing shaped like a NIF or an IBAN.
  - `GET /api/v1/profiles/{id}/calendar` (#70, `src/GestorIA.Api/Profiles/PaymentsCalendar.cs`) answers `PaymentsCalendarView`: every obligation of the profile's tax year (Modelo 130, 303 and 349 each quarter, the monthly TGSS cuota, the Renta true-up), in due-date order, from the set-aside estimate's own `SetAsideResult.Quarters`, `MonthlyCuotas` and `TrueUp`, which `GestorIA.Engine.PaymentCalendar` shapes, so no business rule is duplicated. It runs at `asOf` Q4 on the classified movements' actuals (#73), so every closed, reviewed quarter counts and an unreviewed movement keeps its quarter projected, as in the estimate. Each quarter's Modelo 130 equals what `POST /calculations/quarter?quarter=Qn` answers for it: the actuals up to that quarter are the same run whichever `asOf` reads them, and a quarter's payment depends only on the figures up to it (`PeriodsEndpoint.TheCalendarsModelo130IsEachQuartersOwn`, with no movements, all reviewed and only Q1 reviewed). The calendar has no trace; a quarter's page shows its ledger steps. An obligation's amount is `KnownAmount` or `NotYetKnownAmount` (JSON `kind`-tagged), never a guessed figure: Modelo 303 and 349 have no calculator yet, so they are always `notYetKnown`, on the same window the Reglamento del IVA (RD 1624/1992) art. 71.4 and Orden EHA/769/2010 art. 10.2 share with Modelo 130. Those are the quarterly filer's dates: above `modelo349.quarterlyFilingCap` (SPEC-007; 50,000 € of the entregas de bienes and prestaciones de servicios declared on the 349, IVA excluded, in the quarter or any of the four before, art. 10.2) 349 is monthly under art. 10.1, which the engine cannot tell without intra-EU volumes, so the answer carries the year's figure as `modelo349QuarterlyFilingCap` and the payments page says above it the dates shown no longer apply. Modelo 349's reason also names SPEC-003 §2.1's own condition: a quarter with no intra-EU operations owes no 349 at all, which the payments page and the ICS export both say in words, not only here. The TGSS cuota's due window is new engine law (`FilingDeadline.MonthlyCuotaSs`): RD 1415/2004 art. 56.1.b).1.º makes it due within its own month, and art. 8.b) moves a non-working last day backward, the opposite direction from a filing deadline. So the "municipal holidays are not applied" caveat (Ley 39/2015 art. 30.6) reads differently for it than for a filing: a municipal holiday can make the real date one working day earlier than the one shown, never later. A declared calendar gap (the unpublished 2026 renta window or Q4 Modelo 130 deadline) is the same 422 `config-gap` as the estimate's.
  - `GET /api/v1/profiles/{id}/calendar.ics?amounts=&lang=` (#70) is the profile's *upcoming* obligations, those due today or later (today is Madrid's date, `MadridDay`, from an injected `TimeProvider`, as the export's file name is; past ones already show on the page) as an RFC 5545 export (Ical.Net, `Directory.Packages.props`), for the taxpayer's own calendar app: one one-day all-day `VEVENT` on the due date per obligation (the window, the reason and the local-holidays caveat are in `DESCRIPTION`, not spread across the event's span), a `Uid` stable across exports of the same obligation but unique per profile and tax year (`{kind}-{period}-{taxYear}@{profileId}.gestoria.local`, so a later year's Modelo 130 Q1 never collides with an earlier one's), and no amount or identifier in an event's title unless `amounts=true` is asked for (SPEC-013). `lang` (`uk`, `es`, `en` or `ru`; `en` if left out) picks the event text's language — a small text table of its own (`PaymentsCalendarIcsText`), since a calendar app reads the file directly rather than through next-intl. With `amounts=true` the amount is written the locale's way (`€80.00` in `en`, `80,00 €` in `es`, `uk` and `ru`), from the decimal. When nothing is still to come, as for a tax year that is over, the answer is a 422 `no-upcoming-obligations` rather than a calendar with no events, which RFC 5545 §3.4 does not allow and a calendar app would import nothing from; the payments page says so and disables its export button first. A malformed `amounts` or `lang` is a 400 `invalid-input` with `errors.amounts` or `errors.lang`, like any other query parameter. Both calendar endpoints sit in the profile group, so a lost database is the 503 `database-unavailable` below, and the payments page says so like the overview.
- Opening a period of a stored profile (#71, `src/GestorIA.Api/Periods/`), both reusing the same set-aside estimator as the estimate above, on the same actuals from the classified movements (#73; the true-up with `asOf` Q4, so every closed quarter counts) with the ledger's trace steps before the engine's and the same `ledger { actualsThrough, counted, awaitingReview, awaitingInvoice }` counts, from which the periods page states its basis, and so inheriting the same 2026 gap: `SetAsideEstimator.Estimate` always computes the whole year's true-up alongside whichever quarter was asked for, so on a 2026 profile both endpoints are a 422 `config-gap` for every quarter, Q1 to Q3 included, until both the renta window and the 2027 días inhábiles are published (the latter also feeds the Q4 Modelo 130 due date and every other Q4 working-day calculation) — unlike a direct `Modelo130Calculator.Pago` call (the CLI's own path, README.md "Tax-year configuration"), which can still answer Q1 to Q3 2026 on their own.
  - `POST /api/v1/profiles/{id}/calculations/quarter?quarter=Qn` answers `QuarterResultView`: the quarter's `aIngresar`, due window, `filing` (the same `ingreso`/`aDeducir`/`negativa` the set-aside estimate's `NextPayment` carries), every casilla the Modelo 130 calculator computed (keyed the way `GET /config/tax-years/{year}`'s new `modelo130Lines` names them) and the quarter's own trace. A missing or malformed `quarter` is a 400 `invalid-input` keyed by `quarter`, the same wording pattern as `asOf` on the estimate; a quarter before the alta or a config gap answer the same 422s as the estimate.
  - `POST /api/v1/profiles/{id}/calculations/annual-true-up` answers `AnnualTrueUpView`: the liability the activity income adds, the marginal rate, any reducción por trabajo lost, the gap, its due window and payable-in month, and its own trace and notices. It always evaluates as of Q4, an arbitrary choice: SPEC-002 §5-6's true-up covers the whole year regardless of `asOf`. Its `gap`/`payableIn` equal the set-aside estimate's `annualTrueUpGap`/`annualTrueUpPayableIn` for the same profile.
  - `GET /api/v1/config/tax-years/{year}` now also carries `modelo130Lines`, the casilla numbers the Modelo 130 calculator's own keys mean (`config/tax-years/{year}.json`'s `modelo130.lines`), so a client can label a quarter's casillas without hardcoding AEAT's numbers.
- Bank statements and their movements (#72, `src/GestorIA.Api/Transactions/`), stored under the profile in PostgreSQL:
  - `POST /api/v1/profiles/{id}/bank-statements?bank=bbva` imports a statement. The body is the file itself, sent as `text/csv`, `text/plain` or `application/vnd.ms-excel` (the label Windows gives a `.csv` when Excel is installed); any other `Content-Type`, a form upload or JSON among them, or none, is a 415 `statement-media-type`, after the key check like every refusal. At most 2 MiB (`StatementFile.MaxBytes`; a year of a personal account is well under 200 KB), read before anything else and refused whole above that with a 413 `statement-too-large`. What is not text is refused before parsing: a ZIP archive such as an XLSX workbook, anything holding a NUL byte (UTF-16 among them). The text is UTF-8, with or without a byte-order mark, else Windows-1252. The `bank` adapter parses it (SPEC-004 §5); a file it cannot read is refused whole, with nothing stored, as `invalid-input` whose `errors` are keyed `file` or `line N` and never quote the file. The answer is `BankStatementImport { bank, lines, imported, alreadyImported, from, to }`.
  - **Every import is a statement with a period (#88).** `&from=YYYY-MM-DD&to=YYYY-MM-DD` state it; either left out is the first or last booking date of every line in the file, the lines an earlier import stored included. BBVA's CSV states no period, so the user states the one the statement itself covers. The period must hold every line, may start at most 31 days before the first line and end at most 31 days after the last (`StatementPeriod.MaxDaysBeyondMovements`: an autónomo's account is charged the RETA cuota every month, so a real statement has no month without a movement, and the bound keeps a wrong period well short of a quarter), and may not end after today unless a line does. A malformed date, a period leaving a line out, running more than 31 days past the lines or into days still to come is a 400 `invalid-input` keyed `from` or `to`; a statement with no line is keyed `file`, since nothing bounds its period. Nothing is stored. The import is recorded in `StatementImports { profileId, sequence, from, to }` even when every line was stored before, and its `sequence` is the `ImportSequence` of the lines it stores, taken under the profile's row lock; each movement's `(ProfileId, ImportSequence)` is a foreign key to its import. The answer's `from` and `to` are the recorded period. Installations from before #88 got one import per `ImportSequence`, over the first to the last booking date of its stored lines, numbered 1 to n in their order with the movements following (the migration `StatementImports`; before #88 an import that stored nothing left its number unused).
  - `GET /api/v1/profiles/{id}/bank-statements` answers the recorded imports as `StatementImportView { sequence, from, to }`, ordered by `from`, then `to`, then `sequence`; 404 for an unknown profile.
  - **Idempotent by a key per line.** A line's key is the SHA-256 of its booking date, value date, amount and description, and of its occurrence: the count of identical lines before it in the same file. Two identical coffees on one day are two lines, and a later export covering the same days gives them the same two keys. The balance is not part of the key. A unique index on `(ProfileId, LineKey)` holds it in the database, and imports into one profile run one at a time under the profile's row lock (`SELECT … FOR UPDATE`), so importing a statement again, or an overlapping one, or the same one twice at once, stores each line once. Without an account in the key, two accounts that print the same line on the same day would count it once; accounts arrive with the classifier (SPEC-001 §7).
  - `GET /api/v1/profiles/{id}/transactions?year=YYYY&quarter=Qn` answers the stored movements as `TransactionView { id, bookingDate, valueDate, description, amount, balance }`, money as signed two-decimal strings (positive is money in), in booking-date order; a day's lines follow the order of the imports that stored them, then their line numbers in their files. Both are columns (`ImportSequence`, the profile's imports counted from 1 under its row lock, and `LineNumber`), so neither the clock nor the ids decide the order. Without `year`, every movement; `quarter` needs `year` and filters by booking date. No pagination: a year is a few thousand rows (§1).
  - The movements belong to the profile: a foreign key with cascading delete, so deleting a profile deletes them (SPEC-013, #74).
  - Classification (#73, SPEC-004 §3.1). The rules in `config/transaction-rules.json` classify each movement whenever it is read. The API refuses to start when that file is malformed. The user's decision is the only thing stored (`BankTransactions.Class`).
    - `GET /api/v1/profiles/{id}/review-queue` answers the movements of the profile's tax year that no user decision or certain rule has confirmed, in the list's order: `ReviewItem { id, bookingDate, valueDate, description, amount, suggestion: { class, ruleId } | null }`. Unclear movements have no suggestion; the vendor rule's movements carry one.
    - `POST /api/v1/transactions/{id}/classify` with `{ "class": "activityIncome" }` stores the user's class and answers 204. A later call replaces it. The class is one of `activityIncome`, `deductibleExpense`, `socialSecurity`, `aeatPayment`, `employmentIncome`, `savingsIncome`, `ownTransfer`, `personal`. The body is read as text, so a number, the enum member's C# name (`ActivityIncome`) or a list of names is refused like an unknown class. The error is a 400 `invalid-input` keyed `$`, `$.class` or `$.<unknown field>`. The route names no profile, so the movement must belong to a profile of this installation, else 404 `transaction-not-found`.
    - The estimate's actuals. A quarter is closed when today (the API's clock) is past its last day and it is not after `asOf`. The actuals are the unbroken run of closed quarters from the first quarter of activity, each holding at least one imported movement and none that is unclear or only suggested, and covered by the imported statements: the periods of all statement imports (of any year, and of whatever account a statement came from, since accounts are not modelled yet) are joined where they overlap or meet, and a quarter is covered when one joined period runs from its first day, or the alta when that falls inside it, to one day past its last (so a period ending on a quarter's last day, or starting after its first, leaves it projected until a later or earlier statement meets it, erring towards over-reserving), and into which no quiet stretch of more than 31 days runs (#94): a quiet stretch is the days inside the joined periods, from the alta on, between two consecutive stored movements of the profile (of any year and any import), or from a joined period's start to its first movement, or from its last movement to the period's end. The RETA cuota is charged every month, so a longer one means a statement is missing, even when the periods, each within its own 31-day bound, chain over it. Per quarter, ingresos are the confirmed `activityIncome` and gastos the confirmed `socialSecurity` debits, which are also the RETA cuotas paid (#52). Both are signed sums by booking date. A confirmed `deductibleExpense` counts only with a linked, confirmed invoice (business rule 1), which cannot be stored yet, so none counts. The stored projection is the whole year's; the months the actuals cover drop their share, rounded to cents. Trace steps before the engine's name every movement that counted or waits, by id and booking date only: `ledger.Qn.movements`, `ledger.coverage` when a closed quarter without movements, or one the statements' periods do not cover ("no imported statement's period covers the days from 2025-01-15 through 2025-02-13; Q1 stays on the projection, with what follows, until statements whose periods cover its days from 2025-01-15 through 2025-04-01 are imported", with every statement's period as a `statementPeriod` input, `2025-02-14..2025-12-31`), or one a quiet stretch runs into ("no stored movement from 2025-04-01 through 2025-05-31 (61 days, over 31), though the statements' periods cover those days; Q2 stays on the projection, with what follows, until the statement holding that stretch's movements is imported", with `quietFrom` and `quietThrough` inputs), stops the run, `ledger.pending-review` naming the movements of closed quarters up to `asOf` that await review, `ledger.projection-remaining`. The answer's `ledger { actualsThrough, counted, awaitingReview, awaitingInvoice }` counts them for the overview: `counted` and `awaitingInvoice` in the quarters that are actuals, `awaitingReview` in every closed quarter up to `asOf`.
  - Nothing about a statement is logged: `TransactionsNotLogged` captures every category at Trace while a statement is imported, imported again, refused and listed, its review queue read, a movement classified and the estimate computed from it, and finds none of its descriptions or amounts and nothing shaped like a NIF or an IBAN.
- A database lost after start-up (`src/GestorIA.Api/DatabaseUnavailable.cs`): an exception from any endpoint whose chain holds an `NpgsqlException` that is not a server's answer (a `PostgresException`), or a `PostgresException` about the connection (class `08`, `57P01`–`57P03`), is answered 503 `database-unavailable` instead of an unhandled 500. A unique violation and every other server answer keep their own handling. The body is the same fixed words every time, and the one log line, a Warning, says only that the database is not reachable: Npgsql's message names the host, the port and the database, so the exception is never logged (SPEC-013 §2). EF Core's failure events (`ConnectionError`, `QueryIterationFailed`, `SaveChangesFailed`) are ignored for the same reason; the exception still reaches the handler, and any other failure is logged there as a 500. So are the Debug-level connection and data-reader events (opening, opened, closing, closed, disposing, disposed, `MigrateUsingConnection`), which name the database and its server on every connection. The one place the database's name still reaches a log is the SQL of the start-up migration's `CREATE DATABASE`, the first time it runs. The profile endpoints, export and delete among them, and the transaction endpoints declare the 503 in the OpenAPI document. `DatabaseOutage` stops the test's own PostgreSQL container partway through and holds every answer, and every log line written after the stop at any level down to Trace, to this.
- Problem types (`src/GestorIA.Api/Problems.cs`): `invalid-input` (400, `errors` keyed by the JSON path of each refused value, by the name of a missing or malformed query parameter such as `taxYear`, `asOf`, `bank`, `year`, `quarter`, `amounts` or `lang`, or by `file` or `line N` for a statement), `config-gap` (422: no file for the year, or a value the file lacks or declares unpublished), `estimate-refused` (422: an input only the engine can judge, such as actuals out of order), `no-upcoming-obligations` (422: a calendar export with nothing due today or later), `tax-year-not-found` (404), `profile-not-found` (404), `profile-exists` (409), `transaction-not-found` (404), `installation-not-empty` (409: a restore into an installation that holds other data, §2.2), `statement-too-large` (413), `export-too-large` (413), `statement-media-type` (415), `export-media-type` (415), `api-key-required` (401: no key, more than one, or the wrong one, without saying which), `database-unavailable` (503: the API runs but PostgreSQL does not answer it).
- The web app unlocks only once the key is accepted and `/health/ready` answers: with the database down, the unlock screen says so and shows `docker compose up -d postgres`, as it shows how to start the API when that does not answer. A 503 `database-unavailable` later on the overview, in settings, on the payments page or on the transactions page says the same in the app's language.
- The OpenAPI 3.1 document is generated at build time into `src/GestorIA.Api/openapi/v1.json` and committed. CI fails when it is stale, and oasdiff fails a pull request that breaks the base branch's document (§5). `tests/GestorIA.Api.Tests` validates every set-aside golden's input and every answer against it.
- CORS allows the web app's origin (`Cors:Origins`), the methods `GET`, `POST`, `PUT` and `DELETE`, and its `X-Api-Key` header.
- The local API key of §3 (#68): every endpoint but the health checks answers `401` problem+json `api-key-required` without it.

## 2.1 Export format (#74)

`GET /profiles/{id}/export` answers `ProfileExport`, the file the user keeps outside the machine and what the restore (#75) reads back:

```json
{
  "format": "gestoria.export",
  "formatVersion": 1,
  "classification": "personal-financial-data",
  "exportedAt": "2026-09-28T09:00:00+00:00",
  "entities": {
    "profiles": [ { "id": "…", "taxYear": 2025, "region": "VC", "employment": { … }, "activity": { … }, "projection": { … } } ],
    "statementImports": [ { "sequence": 1, "from": "2025-01-01", "to": "2025-03-31" } ],
    "bankTransactions": [
      { "id": "…", "bookingDate": "2025-01-02", "valueDate": "2025-01-02", "description": "…", "amount": "-12.50", "balance": "1987.50",
        "importSequence": 1, "lineNumber": 7, "lineKey": "<64 hex digits>", "class": "personal" }
    ]
  }
}
```

- `format` is always `gestoria.export`, so a reader can refuse a file that is not an export before it looks further.
- `formatVersion` is an integer. It is raised when a change would make an existing export read differently: an entity kind or a field removed or renamed, or a field whose meaning changes. Adding an entity kind, or an optional field to one, keeps the version. A reader never drops what it does not know: a restore that meets a version, an entity kind or a field it does not know refuses the file rather than restore part of it.
- `classification` labels the file as personal financial data (SPEC-013 §1) wherever it ends up.
- `exportedAt` is the moment of the export, ISO-8601 with its offset, in UTC. The file name the API gives it (`Content-Disposition`, `ProfileExport.FileName`, tested at fixed instants either side of midnight in Madrid) and the web app's download both carry the day of that moment in Madrid (`Europe/Madrid`; ADR-0016's regions are on peninsular time).
- `entities` has one member per table of the database, named after it (`Profiles` is `profiles`, `StatementImports` is `statementImports`, `BankTransactions` is `bankTransactions`), each the list of that table's rows that belong to the profile. `ProfileExportEndpoint.EveryTableOfTheModelIsExportedWithAllItsRows` reads the tables from the EF Core model and fails when a table has no member or a member has fewer rows than the table, so a table added later cannot be left out of the export unnoticed.
  - `profiles` holds the one `ProfileView` (§1.1), with its `id`.
  - `statementImports` (#88) holds every import of a statement in `sequence` order: its `sequence`, which its movements' `importSequence` names, and the period `from` to `to` it covers, both ends included (§1.1). It is optional within version 1: a file without it, as every file exported before #88, restores one import per `importSequence` of its movements, over the first to the last booking date of those movements, the period #73 read from the lines, so the restored estimate is the one the file was made with. The imports are numbered 1 to n in their order and the movements' `importSequence` follows, so a file whose numbers skip one restores, and its next export restores again.
  - `bankTransactions` (#72) holds the profile's statement lines in the list's order (booking date, then `importSequence`, then `lineNumber`), each the `TransactionView` of `GET /transactions` plus what a restore needs to store it again exactly: `importSequence`, the statement import that stored it, and `lineNumber`, which order a day's lines, and `lineKey`, the SHA-256 that keeps a later import of the same statement from storing a line twice (§1.1). With the key restored, importing the statement again after a restore adds nothing. `class` (#73) is the class the user gave the line, or `null` while they have not decided; what the rules make of a line is computed on every read, so it is not in the file. `class` is optional within version 1: a line without it, as in every file exported before #73, reads as `null`, undecided. The restore (§2.2) reads it as `POST /transactions/{id}/classify` does: `null` or one of the classes by the name the API writes; a number, a C# member name or a comma-joined list is a 400 at `$.entities.bankTransactions[i].class`.
  - Money stays a two-decimal string and dates ISO-8601, as everywhere in the API.
  - **A known kind missing from a version 1 file reads as zero rows.** A file exported before #72 has no `bankTransactions` and is still a valid version 1 export: its profile had no stored movements. What a restore refuses is a kind, a field or a version it does not know, never a known kind that is absent.
- The export holds only what the user entered or uploaded, plus the ids, order and line keys the API gave it, and nothing computed: estimates and traces are recomputed from it.

## 2.2 Restore (#75)

`POST /profiles/restore` takes an export file (§2.1) as the body, sent as `application/json`, and stores what it holds. It exists so that a lost laptop does not lose the tax history: install GestorIA again, unlock it, restore the file.

**Only into an empty installation.** Local mode keeps one profile per installation (§1.1), so a restore either fills an empty installation or finds one already in use:

- Nothing stored: everything in the file is stored in one database transaction, all or nothing, and the answer is 201 `RestoredExport { profileId, entities: { profiles: 1, statementImports: M, bankTransactions: N } }` with `Location` on the profile. `entities` counts what was stored, one member per entity kind of the export.
- The installation already holds exactly what the file holds (the same profile under the same id, the same movements with the same ids, order and keys): nothing is written, and the answer is 200 with the same body. So the same file sent twice, or sent again after an answer was lost, leaves the same state and succeeds both times. Two restores of one file at once store it once: the second is refused by the profile's unique index and then finds the first's rows.
- Anything else stored: 409 `installation-not-empty`, naming what is there in `detail` and as extensions (`profileId`, `taxYear`, `entities` with the count per kind), and nothing is written.

There is no replace. Deleting everything already has its own action, behind a typed confirmation that lists what goes (#74); a flag that deletes as a side effect of a restore would be a second, quieter way to lose the data. To replace what is stored, download a copy of it, delete it in settings, then restore.

**Validated at the boundary, the whole file before anything is written.** In this order, and a file refused at one step is not looked at further:

1. The `Content-Type` is `application/json`, else 415 `export-media-type`. At most 16 MiB (`ProfileRestore.MaxBytes`: a movement is about 250 bytes of JSON, so decades of a personal account), read before anything else and refused whole above that with 413 `export-too-large`.
2. `format` is `gestoria.export` and `formatVersion` is a version this API reads (1), checked before the rest is read, so a file from a newer GestorIA is refused for its version and not for the first field it adds.
3. Every member of `entities` is a kind this API knows; a known kind that is absent reads as zero rows (§2.1). Every object holds only the fields of its type, with the types the export writes: a field this API does not know is refused, never dropped, so no `profileId` on a movement can point it at another profile.
4. The values, every refused one named at once in `errors` by its JSON path (`$.entities.bankTransactions[3].lineKey`); no message quotes a movement's description:
   - `classification` is `personal-financial-data`, and `profiles` holds exactly one profile. No element of a kind is `null`, and no id is `00000000-0000-0000-0000-000000000000`: EF Core would store a key of its own in its place, and what is stored would no longer be what the file holds. A string holding half of a character (a lone `\ud800`) is refused wherever it is.
   - The profile passes the same checks as `POST /profiles` (`ProfileInput`): amounts, a tax year this installation has a configuration for, its region, the alta, the base de cotización.
   - Each movement's `amount` and `balance` are euros with at most two decimals and twelve digits; its `description` passes the same rule a statement line's does (`StatementDescription`, which the BBVA parser applies too): no NUL, no line break, no leading or trailing space, only whole characters; `lineNumber` is at least 1; `importSequence` names a statement import of the file, or, in a file without statement imports, is at least 1 and at most the number of movements in the file, since before #88 only an import that stored a line kept its number; ids are distinct, and so are `(importSequence, lineNumber)` pairs.
   - Each statement import's `sequence` is from 1 to the number of imports in the file and no two share one. Its period passes the import's own rule (§1.1) against its statement's movements, which are the ones whose `importSequence` names it and every movement of the file inside its period (an import that stored nothing new has only these): it holds each of them, runs at most 31 days past them, and does not end after the restore's day unless one of them does. An import with no movement at all is refused at its path.
   - **Line keys are checked, not trusted.** An import stores every occurrence of a line it has not stored yet, and a file that holds a line's k-th occurrence holds the first k, so the movements that print the same (booking date, value date, amount, description) always carry the keys of occurrences 1 to n. A group whose keys are not exactly those is refused. A key changed by hand would otherwise let a later import store a line twice, or never.

`NoFileIsAnsweredWithA500OrWrittenInPart` gives every node of a real export, down to each field of a movement, each value of the wrong kind (null, numbers, text, a NUL, half a character, arrays, objects) and leaves each member out: every answer is a refusal with nothing stored, or the whole file stored. Nothing is logged of the file: `ProfileNotLogged` and `TransactionsNotLogged` restore, restore again and restore refused files while capturing every log category at Trace (SPEC-013 §2).

**The round trip.** `ProfileRestoreEndpoint` seeds a row in every table of the EF Core model, exports, deletes, restores and exports again: the two documents are equal apart from `exportedAt`, every table holds as many rows as before, and the answer counts one member per table. A table added later that the restore does not carry fails it, as it fails the export's and the delete's tests.

The web app's Backup page reads the file in the browser and shows what it holds (the count per kind, the profile's tax year and region, the first and last booking date) before anything is sent; the restore happens only when the user confirms (`web/README.md`, "Export, restore and delete").

## 3. Auth
v1 local mode: single user, API key in header. OIDC (Authorization Code + PKCE) behind a feature flag for hosted mode; all resources scoped to the authenticated user.

Local mode as built (#68, `src/GestorIA.Api/ApiKey.cs`):
- The client sends the key in `X-Api-Key`. The OpenAPI document declares it as the `apiKey` security scheme on every operation but the health checks, which stay open so a client can tell "not running" from "locked".
- Configuration holds only the key's SHA-256 (SPEC-013 §2), as `Auth:ApiKeySha256`: user secrets on a development machine, the `Auth__ApiKeySha256` environment variable elsewhere, never a file in the repository. The API refuses to start without a usable hash, including the hash of an empty key.
- The presented key is hashed and compared with `CryptographicOperations.FixedTimeEquals`, so the comparison takes the same time however much of it matches.
- The check runs as middleware before parameter binding, on every path under `/api/v1` but `/api/v1/health`, whatever endpoint routing chose: a locked route asked with the wrong method or `Content-Type`, or a path that does not exist, is a 401 like any other request without the key, not a 405, 415 or 404 that would tell a caller which routes exist. A request without the key does no other work. CORS preflights are answered before the check. The locked route group only declares the key in the OpenAPI document. In Development the API also serves its OpenAPI document at `/openapi/v1.json` without the key: it is the committed `v1.json` and holds no data. Nothing logs the key: `ApiKeyNotLogged` captures every log category at Trace while the key is used, mistyped and left out.

## 4. Errors
`400` validation (field errors), `404`, `409` (document already confirmed), `422` (calculation cannot run: missing config/region, unconfirmed required docs — body lists blockers), `503` (OCR unavailable — upload accepted and queued anyway; `database-unavailable` when PostgreSQL cannot be reached, §1.1).
