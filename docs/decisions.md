## Small decisions (no ADR)

- **One taxpayer profile per local installation, its tax year a field** — 2026-09-27, #69. SPEC-001 calls the profile "per year"; with one user and one dashboard, one profile whose year is chosen in settings is enough, and a second `POST` is a 409. The database holds the rule (a unique index on an always-true column), not only the handler, so racing creates store one profile. Per-year profiles return with a second year to compare or a second user.
- **A new profile starts on the newest tax year whose configuration declares no gap** — 2026-09-27, #69. The newest year, 2026, refuses every set-aside estimate until its renta window is published (around March 2027), so defaulting to it would greet a first profile with a refusal. A gapped year stays selectable, with its gaps listed in settings, and its estimate shows the 422 as "not published yet". The default moves on by itself when `2026.json` closes its gaps or `2027.json` lands complete.
- **The API migrates its database as it starts** — 2026-09-27, #69. One user, one local database: `Database.MigrateAsync()` at start-up is idempotent and saves a setup step. It is skipped while `dotnet build` generates the OpenAPI document. Revisit with a second instance or a hosted database, where migrations become a deployment step.

- **A bank statement line is keyed by what the bank printed and how many identical lines precede it** — 2026-09-28, #72. Re-importing a statement, or a later export overlapping it, must not duplicate money, and two genuinely identical lines on one day (two coffees) must stay two. A key of booking date, value date, amount and description alone would merge the coffees; adding the file position would duplicate every line of an overlapping export. Counting occurrences within the file keeps both right, as long as an export never cuts a day in half; one that does can only add the missing twin on the next import, never drop a line. The database holds the key with a unique index, and imports into one profile are serialized by the profile's row lock. The statement's line is `BankTransaction`, which replaced the prototype `Transaction` in the same change (SPEC-001 §7).
- **A statement arrives as the request body, not a multipart form** — 2026-09-28, #72. One file per request, so the body is the file and `?bank=` names its adapter. The handler reads at most one byte over the 2 MiB limit and refuses above it, which a test can see in-process, and needs no antiforgery exemption, which a form upload in minimal APIs asks for. The body's `Content-Type` must be one a browser gives a CSV file (`text/csv`, `text/plain`, `application/vnd.ms-excel`); anything else is a 415. Document uploads (SPEC-005) keep multipart, where metadata travels with the file.
- **A restore fills only an empty installation; there is no replace** — 2026-09-28, #75. The same file again is a 200 that writes nothing, so a retry is safe, and any other stored data is a 409 naming what is there. Replacing is "download a copy, delete in settings, restore": the delete keeps its typed confirmation as the only way to lose data, instead of a restore flag that deletes on the side. The file's line keys are checked against its movements rather than recomputed, because a key that does not fit means the file was edited, and silently fixing it would change which lines a later import stores (SPEC-009 §2.2).
- **The restore preview is read in the browser** — 2026-09-28, #75. The Backup page parses the chosen file and shows its counts, tax year and date range before sending anything; the API validates the whole file when the user confirms. A server-side dry run would validate earlier, but it would send the whole of the user's data twice and add an endpoint, and a refusal at confirm writes nothing anyway.
- **Only the user's classification is stored; the rules' is computed on every read** — 2026-09-28, #73. `BankTransactions.Class` holds what the user decided, or nothing. The rules live in `config/transaction-rules.json` (SPEC-004 §3's order, first match wins) and run whenever a line is read. So #72's lines need no backfill, and a rule edited in the file reclassifies every line the user has not decided. Storing the rules' answer too would need a migration for old lines and a re-run after every rule change, and would give a row two sources of truth.
- **A rule confirms only a debit whose class counts nowhere; everything else it only suggests** — 2026-09-28, #73. A rule that confirms without the user moves money nobody confirmed whenever it is wrong, so the rules file is refused at start-up in two cases. First, a `certain` rule for credits: a credit could be activity income, and confirming it as anything else takes it out of the actuals (a client called Hacienda Los Olivos SL, a transfer from AEATX Consulting, a payment described as nominal). Second, a `certain` rule whose class enters a figure of the estimate: activity income, the RETA cuotas (`socialSecurity`, which enters gastos and the cuotas paid) and deductible expenses (`LedgerActuals.Counts`, the same table the actuals are summed by). A TGSS debit may be a domestic employee's cuota, a surcharge or a colegio's fee, and confirming it as the titular's RETA cuota lowered a Modelo 130 with nothing queued. Neither check covers the other: a certain credit rule into a class that counts nowhere would still hide activity income. So TGSS debits, salary, savings and AEAT refunds wait in the review queue with the rule's suggestion first, which costs a keypress a month; a TGSS credit gets no suggestion, since it is a benefit or a refund of cuotas and suggesting either puts the wrong one a keypress away. What stays certain are debits into classes outside the activity: AEAT payments and personal spending. Such a line is not the activity's rendimiento (LIRPF art. 28) and enters no figure, and whether its quarter is actuals depends on the dates the statement reaches, not on the line (next entry). So a wrong certain match can only leave money that counts out of the estimate, which over-reserves: `CUOTA RETA DIA 30` is confirmed personal through `DIA `, and `AGENCIA TRIBUTARIA RECARGO CUOTA RETA` an AEAT payment, each hiding a real cuota, and a certain match can hide a deductible expense once invoices exist. The user can reclassify any of them. SPEC-004 §3.1 lists the known false matches.
- **A deductible expense does not count until invoices exist** — 2026-09-28, #73. Business rule 1 asks for a linked, confirmed `FacturaRecibida`, and GestorIA cannot hold one before document ingestion (SPEC-005). A line the user confirms as a deductible expense is recorded but left out of the actuals. The estimate's trace names it and the overview says how many wait. This over-reserves: the actual gastos of the closed quarters are the RETA cuotas alone. Such lines stay out of the review queue, because nothing in the app can resolve them yet.
- **Confirmed activity income counts at the amount credited** — 2026-09-28, #73. Business rule 4 rebuilds a payment from its invoice. The estimator serves only the SPEC-003 §0 client mix (no IVA, no retención), and for that mix the amount credited is the invoice base. Not counting income until invoices exist would under-reserve. A booking date puts a line in its quarter: this approximates devengo (business rule 3) by the cash date until invoices carry the accrual date.
- **A closed quarter becomes actuals only when the imported movements reach past it and none of its movements awaits review** — 2026-09-28, #73. A quarter is closed when today is past its last day and it is not after the estimate's quarter. The actuals are the unbroken run of closed quarters from the first quarter of activity, each holding at least one imported movement, none that awaits review, and ending before the latest booking date of any movement the profile holds. Each condition guards against reading missing income as zero. A quarter with no movements has no evidence. A quarter with an unreviewed movement has income nobody knows yet: counting it with the unreviewed lines left out was tried first, and a statement just imported turned every quarter of a past year into actuals with no income, so the estimate refused to run. A quarter the statement stops inside may hold income not imported yet: a statement exported on 22 April holds three weeks of Q2, and counting Q2 from them read the rest of Q2 as zero and lowered its Modelo 130 to 0.00. "The quarter has some lines" is not "the statement covers the quarter", whoever classified the lines. A BBVA export does not say which days it spans, so the latest booking date is the evidence, and a statement ending on a quarter's last day leaves that quarter projected until a later movement arrives. That is conservative, and a later import fixes it. The trace says where the run stopped and why, and names the movements that wait.
- **The stored projection is the whole year's; months the actuals cover give up their share** — 2026-09-28, #73. Settings asks for the year's expected ingresos and gastos once. When quarters close, the estimate keeps `projection × projected months / months of alta` of each, rounded to cents, and the trace shows the sum. The alternative was asking the user to restate the projection every quarter, and a forgotten restatement would count the closed months twice. The estimator already spreads its projection evenly over the months, so nothing new is assumed.

- **There is a web app, and the CLI stays** — 2026-09-27, settling the CLI-or-SPA question that was deferred to M3. The author chose a Next.js web app in `web/` (ADR-0017, #65).
- **Regions in v1.0: Valencia (`VC`) and Madrid (`MD`)** — 2026-09-27, superseding the 2026-09-18 note that kept Valencia only. Both are complete in every tax-year file, and the schema requires both (ADR-0016).
- **Build order follows deadlines, not scope** — 2026-09-18. Quarterly forms first, because the author registers as an autónomo in January 2027 and Modelo 130 and 303 for Q1 2027 fall due 20 April 2027, alongside Renta 2026 (ADR-0014). The autónomo annual path is not needed until April 2028.
- **PostgreSQL, EF Core and ASP.NET stay in v1.0** — 2026-09-18, closing a challenge raised and withdrawn the same day. ADR-0006 stands unchanged. The deciding argument is not volume, it is `decimal`. SQLite has no decimal type, EF Core maps `decimal` to TEXT there, and ordering and comparison on money break. ADR-0004 makes `double`/`float` for money a build error, so a store that cannot hold an exact decimal is disqualified before convenience is discussed. PostgreSQL `numeric` holds it exactly. The ledger is also genuinely relational (transaction → linked document → invoice) with immutable versioned rows per SPEC-001 §5, and the Phase 3 learning track lists EF Core and ASP.NET as goals.
- **Retención is a property of the payer, not the issuer** — 2026-09-18. See business rule 3b. This was latent in SPEC-001, where `AutonomoRegistration.RetencionRate` looks like it belongs on the invoice.
- **v1.0 produces the Modelo 349 itself** — 2026-09-18, not just per-client totals. The data is a by-product of the 303 calculation, and a quarter with no intra-EU operations producing no filing is part of the output.
- **A gestor prepares Q1 2027 in parallel** — 2026-09-18. The 130, 303 and 349 have no borrador and no simulator, and the author's first quarter combines tarifa plana, EU reverse charge, US export and zero retención, which no worked example covers. Q1 is filed from the gestor's numbers; the diff against the engine becomes `gestor-prepared` goldens; Q2 2027 is the first self-filed quarter.
- **Commits are authored solely by the repository owner** — 2026-09-18. Enforced by `.githooks/commit-msg`, not only documented. See `docs/CONVENTIONS.md`.
- **VIES verification is recorded by hand in v1.0** — 2026-09-18. `Client.Vies { Number, VerifiedOn }` plus a warning at invoice time when it is missing or stale. The VIES consultation reference is the evidence worth storing, and an automated call that returns a boolean discards it.
- **Golden oracles are ranked** — 2026-09-18. `aeat-simulator`, then `published-example` with a citable reference, then `theory`. Tax-advisor articles find rules; they do not fix numbers (SPEC-011 §1).
- **Credits are the destination, not a mid-plan phase** — 2026-09-18. Renta WEB already produces a borrador with most figures in it. What it does not do is tell you which regional credit you missed. SPEC-006 and SPEC-010 are what v1.0 is for; SPEC-002 exists to make them evaluable.
- **The first filing is Renta 2026, due April to June 2027** — 2026-09-18. The first production config is therefore `2026.json`, not `2025.json`.
- **The prototype is deleted, not kept green** — 2026-09-18. `IrpfTaxCalculator`, `IrpfCalculationResult` and their tests are gone. SPEC-001 §7 and SPEC-011 §4 previously said to keep them compiling until the goldens passed; they had already stopped compiling. `IStatementParser`, `BbvaCsvStatementParser`, `Transaction` and `BbvaParserTests` survive, because SPEC-004 §5 carries them forward. (`Transaction` became `BankTransaction` on 2026-09-28, #72.)
